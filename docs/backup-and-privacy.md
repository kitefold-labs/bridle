# Backups and crash reports

Bridle has no accounts, no cloud sync and no servers. This page explains the two features that
move data off your phone, and only when you ask them to: **encrypted backups** (how you move your
setup to a new phone) and **crash reports** (filed by you as GitHub issues).

## Encrypted backups

### What a backup contains

- Hosts: label, hostname, port, username, group, jump host, tags, color, favorite flag,
  keep-alive, default tmux session, startup command and environment variables
- Groups, Launch Profiles, snippets and port forwards
- Known hosts: the host keys you have trusted, with their fingerprints
- Key *metadata*: each key's name, algorithm, public key and whether it was generated on the
  phone or imported

Anything you typed into a host or profile is included, environment variables too. If you keep an
API token in a host's environment, it is in the backup. It is encrypted with your passphrase like
everything else.

### What a backup never contains

- **Private keys.** This is deliberate.
  - Keys generated by Bridle live in your phone's secure hardware (the Android Keystore) and
    cannot be exported, by anyone.
  - Keys you imported are stored encrypted and are never exported again, so a stolen backup
    plus a weak passphrase can't turn into a stolen key.
- **Passwords.** Bridle never stores them, so it can't export them.
- Terminal scrollback, session history or anything else you saw on screen.

### Restoring on a new phone

1. On the old phone, export a backup from Bridle's settings. Choose a passphrase of at least 10
   characters and save the file somewhere the new phone can reach.
2. On the new phone, import the file and enter the passphrase.
3. Bridle shows what it will import before it changes anything:
   - **Already present.** Entries that match something on this phone are skipped and your
     existing entry is kept. A host matches on hostname, port and username; a snippet on name
     and body; a Launch Profile on host and tmux session; a known host on host, port and key
     type.
   - **Host key conflicts.** If the backup trusts a *different* key for a host this phone
     already trusts, the phone's key is kept and both fingerprints are shown. That includes a key
     of another type (say ECDSA where the phone trusts Ed25519): Bridle never replaces a trusted
     host key silently, and never adds a second one behind your back either.
   - **Missing keys.** Hosts that used a key which isn't on this phone are imported without a
     key, and Bridle lists which hosts need one. Generate a new key (or import your own) and use
     **Add this device's key to all hosts** to install it. If you import the *same* key you
     used before, hosts are linked to it automatically, matched by public key.
   - **Skipped entries.** Anything that fails the same checks as manual input (an invalid
     hostname, a bad tmux session name) is left out and listed.

### How the file is encrypted

A backup is a single binary file:

| Bytes | Content |
|------:|---------|
| 8 | `BRIDLEBK` signature |
| 1 | format version (`1`) |
| 1 | key-derivation function (`1` = Argon2id) |
| 9 | Argon2id cost: memory (KiB), iterations, parallelism |
| 16 | random salt |
| 12 | random nonce |
| rest | AES-256-GCM ciphertext of the configuration (JSON), plus a 16-byte authentication tag |

- The encryption key is derived from your passphrase with **Argon2id** (64 MiB of memory, 3
  passes by default), so each guess at a passphrase is slow and memory-hungry.
- The data is encrypted and authenticated with **AES-256-GCM**. The whole header is
  authenticated too, so tampering with any byte, including the cost parameters, makes the import
  fail.
- A wrong passphrase and a damaged file look the same: "Wrong passphrase, or the backup file is
  damaged". There is no recovery: if you forget the passphrase, the backup can't be opened.
- Files that declare absurd cost parameters are rejected before any work is done, so a crafted
  file can't freeze the app.

Choose a long passphrase. A few random words work well, for example four or five words from a
word list. Anyone with the file can try passphrases offline at their own pace.

## Crash reports

Bridle has no crash-reporting SDK and sends nothing automatically.

1. If Bridle crashes, it saves a **scrubbed** report on the phone.
2. On the next launch it asks whether you want to report it, and shows you **the exact text**
   that would be sent.
3. If you agree, Bridle opens a pre-filled GitHub issue in your browser, using the repository's
   *Crash report* template. Nothing is sent until you press **Submit** on GitHub, and you can
   edit or delete anything first.

### What a report contains

- Bridle version, Android version and device model, and the time of the crash
- Exception types and their messages, **after scrubbing**
- Stack frames: class, method, source file and line number from Bridle's own code and the
  libraries it uses. Bridle's own frames are always kept. Long runs of framework frames are
  shortened, and the whole report is size-capped.

### What scrubbing removes

Exception messages sometimes quote the values that caused the problem. Before a report is saved,
Bridle replaces:

| Found | Replaced by |
|-------|-------------|
| Hostnames such as `devbox.tail1234.ts.net` | `<host>` |
| IPv4 and IPv6 addresses | `<ip>` |
| `user@host` | `<user>@<host>` |
| Email addresses | `<email>` |
| File paths (`/home/…`, `/Users/…`, `/data/user/…`, `/storage/…`, `~/…`, `./…`, `../…`, other absolute paths, Windows and network paths) | `<path>` |
| URLs | `<url>` |
| `SHA256:` and MD5 key fingerprints | `<fingerprint>` |
| Long hex or base64 strings (possible keys or tokens), also as `key=value` | `<redacted>` |
| The names, hostnames and usernames from your own configuration | `<redacted>` |

Terminal content is never part of a report. Scrubbing errs on the side of removing too much: a
file name may show up as `<host>`. It works on the *shape* of text, so some things can't be
recognised: a short password, a single-word host name that isn't in your configuration, or a
folder name with a space in it. Please still read the report before you submit it. If you
spot something private that was missed, delete it and
[tell us privately](../SECURITY.md) so we can fix the scrubber.

Anything you type in the "What were you doing?" box is sent as you wrote it.

## For developers

Both features live in the pure-JVM module `:core:backup`:

- `BackupPayload`, `BackupCrypto`: export format and encryption
- `BackupMerge` → `ImportPlan`: the import plan, with id remapping, duplicate detection and
  conflict reporting
- `Scrubber`, `CrashReport`, `GitHubIssueUrl`: crash reports

See also [SECURITY.md](../SECURITY.md) and [02-architecture.md](02-architecture.md) §4, §6
and §11.
